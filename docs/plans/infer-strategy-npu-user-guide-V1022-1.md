# 推理策略寻优工具使用指南

---

## 1 简介

### 1.1 工具介绍

`infer-strategy-npu` 是一款面向大模型推理部署的策略寻优工具：它以内置的**算子级性能模型**为基础，通过对各模型架构拆解为 GEMM、Attention、MoE 与集合通信等核心算子在目标硬件上的时延建模，并据此在给定模型、卡数与 SLO（TTFT / TPOT）约束下，给出 **PD 混部 / PD 分离** 两种场景下的模型最优推理策略。

| 功能 | 说明  |
| --- | ---  |
| PD 混部 | Prefill 与 Decode 运行在同一实例中，适合快速评估整体吞吐 | 
| PD 分离 | Prefill 与 Decode 分开部署，自动搜索PD节点配比和评估节点吞吐 |

### 3.2.3 实测结果与准确率对比

**实测方法：** 在 910B 上按候选配置真实部署，记录端到端输出吞吐并据此重排。

**实测结果：** 最优配置为 `tp1pp1`（8 副本），排名为 **tp1 > tp2 > tp4 > tp8**。

| 对比项      | 真机实测          | 本工具预测                   | 华为工具预测             |
| -------- | ------------- | ----------------------- | ------------------ |
| Top-1 配置 | `tp1pp1`      | `tp1pp1` * 8 副本（一致）        | `tp4dp2`（实测第 3 ） |
| 完整排名     | 1 > 2 > 4 > 8 | **1 > 2 > 4 > 8**（一致） | 4 > 8 > 2（错位）    |

**结论分析：**

- 本项目在 ISL/OSL = 128 工况下，**Top-1 命中、Top-4 完整排名与实测完全一致**；
- 昇腾工具 Top-1 预测为 `tp4dp2`，实测列第 3，Top-3 排名错位；原因：昇腾工具不具备在NPU资源充足的条件下开启副本数搜索。
- 底层差异：
  - 本工具：通过算子实测表，加载GEMM/Attention/MLA/MoE/HCCL等实测数据，利用键为(m, n, k) ，并通过算子对稀疏网格做线性插值以实现各维度张量下算子时延估算。
  - 昇腾工具：通过按计算图里每个算子的真实张量形状算纯解析roofline。具体为在模型经过图改写/融合/切分之后，按实际要执行的计算图、真实张量形状来估性能。


### 3.3 结论

**本工具的优势**：
1. 基于真机采集的算子性能推算，比理论公式估算更准。
2. 全空间寻优分钟级出结果，华为同类大模型搜索时间更长。

**华为工具的优势**
1. 新模型只给配置即可评估，不依赖性能库，更便于快速验证。


**后续优化**
1. 借鉴华为工具"配置驱动、快速适配新模型"的能力，解决我们模型适配慢、新模型无结果的问题。


### 3.4 后续规划

1. 借鉴华为工具"配置驱动、快速适配新模型"的能力，解决我们模型适配慢、新模型无结果的问题。
2. 功能扩展：面向给定业务负载、SLO要求及芯片显存配置，进行PD节点推理资源容量规划，评估并推荐满足服务性能约束所需的NPU卡数量。

## 附录 C 昇腾MsModeling工具框架分析

### 第 0 层：把命令翻译成"要搜什么"

- 命令里没指定并行切法时，工具**默认只搜 TP（张量并行）这一维**，按 2 的幂遍历：TP=1,2,4,8,16,32,64,128，共 8 个候选。
- 硬件画像提供所有"天花板"数字：算力峰值、HBM 带宽、卡间互联带宽，以及每个算子固定要付的启动开销（微秒级）。
- GLM-5.2 是个 MoE 模型（288 个专家、每次激活 8 个），混合了两种注意力，KV 缓存有一套特殊规则（MLA 的 KV **不随 TP 切分**）。

### 第 1 层：并行枚举（搜几种切法）

- 8 个候选各自丢进一个独立子进程并行计算（默认 8 进程）。
- 单卡数不满足整除关系的组合直接跳过。
- 每个候选都会**重新构建一遍模型**（因为是仿真，构建很快、不占显存）。

### 第 2 层：并发搜索（每种切法搜几个并发）

- 先自动选一个"每步最多处理多少 token"的预算（三档降级，显存放不下就调小）。
- 并发数搜索：先用最小并发探一下，再指数放大、最后二分精化，找到满足时延上限的**最大并发**。
- 三个"不达标"判据，优先级是：**显存爆了 > 每字时延超 > 首字时延超**。本例GLM5.2业务要求宽松，真正的瓶颈通常是**KV 缓存把 64GB 显存吃光**。

### 第 3 层：指标合成（时延怎么变成吞吐）

- prefill 阶段：所有请求排成波次依次做 prefill，TTFT = 所有请求"出首字时刻"的平均值（排队模型）。
- decode 阶段：每条请求反复吐字，TPOT = 单步 decode 时延 + 首字时延摊到每个字上。
- 吞吐 = 总并发 / 平均每条请求的端到端时延（Little 定律）。
- 本例输出长度 1024，首字时延摊到每字很小，所以**吞吐基本由"单步 decode 多快 × 总并发"决定**。

### 第 4 层：一次前向的毫秒数从哪来（最核心）

- 在"假设备"上构建模型（只带形状、不占显存），抓取每一步算子的调用。
- 对每个算子用 **roofline 公式**估算耗时：`耗时 = max(算力时间, 访存时间) + 固定开销`。
  - 算力时间 = 运算量 / 算力峰值；访存时间 = 数据量 / 带宽。
  - 大并发时算力是瓶颈，小并发时搬数据是瓶颈。
- 通信算子（TP 的 all-reduce、MoE 的 all-to-all）按"卡在机内还是跨机、用 ring 还是 tree"自动选最快算法估算。
- 一次 decode step 大致由：45 层注意力/线性注意力计算 + 每层 1 次 TP 通信 + MoE 层 2 次跨机 all-to-all + 一堆微秒级固定开销组成。


## 附录 D 工具异同

### 链路异同

**相同点：**

- 都是离线寻优：枚举并行候选 → 对每个候选估算 TTFT/TPOT/吞吐 → 用 SLO 约束过滤 → 帕累托/top-N 排序。
- 都纯 CPU、不占 NPU、不下真实推理：aic-npu 是算子查表 + 数值合成；msmodeling 是 meta device 上的计算图仿真。
- 都做 agg vs disagg 对比（aic-npu 内置 agg/disagg 两个 experiment；msmodeling 用 --disagg）。

**区别：**

- aic-npu 的"模型"是按架构列出的算子清单为整体（context_ops/generation_ops），每个算子只 query(database)（operations.py，无 nn.Module、无 forward）。
- msmodeling 真的把模型按 config 构建成 torch 模块（在 meta 上），并 torch.compile 成 FX 图（含 MLA 融合 / dispatch FFN combine / SP 等图改写），再逐算子估算。
