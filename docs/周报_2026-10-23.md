## 二、问题明细

### 1. 950DT 镜像前置环境：`/lib64` 软链（triton 类采集器必做）

**现象**
- triton 的 Ascend 后端首次启动 kernel 要现编 `npu_utils.so`，链接 `-lascendcl`/`-ltorch_npu` 时把它们的 `DT_NEEDED` 拖进来；这些库在 CentOS 系构建，`DT_NEEDED` 写死绝对路径 `/lib64/libm.so.6`、`/lib64/libmvec.so.1`、`/lib64/libc.so.6` … Ubuntu aarch64 容器没有 `/lib64` →
  ```
  /usr/bin/ld: cannot find /lib64/libm.so.6
  clang: error: linker command failed with exit code 1
  RuntimeError: Failed to compile .../npu_utils.cpp
  ```

**两层影响**
1. **GDN**：`chunk_gated_delta_rule` 是 triton kernel，启动前必须加载 `npu_utils.so` → `AssertionError: Device properties not initialized`。表现为**点位奇偶交替失败**（conv 是 `_C_ascend` 自定义算子不走 triton，故奇数过、偶数挂）。
2. **DSv4 / MLA**：不直接用 triton，但每个点位都会重试一次 `init_device_properties_triton` → 每点白花 ~6 s。

**修复**
- 系统里存在的库逐个软链；aarch64 glibc **不含** `libmvec`，用空壳 so 顶上（`npu_utils.cpp` 只是 pybind 壳，不调向量数学）。
- 用 `readelf -d ... | grep NEEDED` 兜底扫出新出现的 `/lib64/xxx`。
- 完整脚本 + 验证命令已写入文档 `docs/DATA_FROM_SCRATCH_3_MODELS - 950迁移版.md` **§2.1**。
- 注意：`/lib64` 非标准目录，loader 默认不搜它，不影响系统，但**容器重建会丢，需写进镜像/启动脚本**。

### 2. NPU graph 抓图模式（GDN 偶数点位）

**现象**
- 报 `Not_Supported(EE1016): Synchronizing a stream failed` / `ERROR 107030 aclrtMemcpy` / `operation not permitted when a stream is capturing and the specified capture mode is not relaxed`。

**根因**
- `chunk_gated_delta_rule_fwd_h` 的 `cu_seqlens` 只接受**主机端 int 列表**，每次调用做一次 H2D 拷贝；Ascend 只在 **RELAXED** 抓图模式允许此类操作，默认 GLOBAL(0)/THREAD_LOCAL(1) 直接 abort。

**修复过程**
1. ❌ 初版「先 GLOBAL、失败再换新流 + thread_local/relaxed 重试」——**不成立**：Ascend 抓图失败后**线程留在 capture 态**，后续任何模式/流重试都报 "thread is in the capture state"，重试只会污染 eager 回退。
2. ✅ 改为**单次抓图 + 调用方指定模式**：
   - `collector/bench_engine.py`：删掉渐进重试，新增 `graph_capture_error_mode` 参数（也可经 `$AIC_NPU_GRAPH_CAPTURE_MODE` 全局覆盖）；`torch_npu` 不支持该参数时自动退回默认模式。
   - `collector/npu/collect_gdn.py`：仅对 triton scan（`chunk_gated_delta_rule`）传 `"relaxed"`，conv / recurrent 保持默认 GLOBAL（它们本来抓得住，不带此包袱）。

### 3. DSv4 / MLA 采集器 A5 适配（已提交 9dc2073）

- `collector/npu/dsv4_factory.py`
  - A5 indexer 的 `k_cache` 分配改为 `(k, scale, full)` **三元组**（修复 `IndexError: tuple index out of range`）；新增 `_is_a5_device()`。
  - A5 合成 `o_proj` FP8：`wo_a.weight` + `e8m0 weight_scale`（`dsa_v1` 仅实现 FP8 分支）。
- `collector/npu/collect_dsv4_attn.py`
  - A5 仅允许 `num_heads_q` 为 **64 / 128**（kv-quant 稀疏注意力算子硬校验，否则 AICPU 异步失败 `0x2a` → 全卡 `507018`）。
  - `finally` 不再静默吞掉 NPU synchronize 错误，并保护 `empty_cache`。
- `collector/npu/mla_module_factory.py`：`init_device_properties_triton` 每进程只尝试一次（避免每点重跑 clang++ 编译，950DT 上必然失败白花 ~6 s/点）。
- `collector/npu/collect_gdn.py`：A5 强制 `import vllm_ascend_C` 注册 `torch.ops._C_ascend`（`enable_custom_op` 在 A5 上整体 disable）；triton 设备属性获取失败时回退 `torch_npu` core 数。

### 4. 全量采集脚本第 14 段失败（进行中）

- 现象：`§4.7 attention head_dim=256 (Qwen3.8-27B)` **FAILED `rc=127`（369 s）**；第 15 段转换段虽标 OK（0 s）但无 attention 产物（源缺失）。
- 分析：`rc=127` 通常 = "command not found"，但同款 `python collect_attn.py` 其它段正常且本段跑了 369 s 才退，更像是底层（NPU 驱动 / triton 编译链）异常终止后 shell 归一成 127。脚本注释已注明 950DT 的 FIA 对 `head_dim=256` 可能受限于 128/192 上限。
- 待办：取日志尾部定位崩溃点（`awk '/attention head_dim=256/{p=1} p' $LOG | tail -80`）；可 `ONLY=attn bash tools/collect_3models_from_scratch-950DT-ckw.sh` 配合 `--resume` 单段补采。
